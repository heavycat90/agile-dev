# 版本实施与发布

> 迭代开发流程第四、第五步（交付Agent专用）：支持标准通道（从 `plan/to-do/` 拉取）和快速通道（从分流决策直接接手），实施、验证、记录并提交。
>
> 本文件由交付Agent使用。交付Agent 负责阶段 4-5，实施代码变更、验证发布。交付Agent 不修改 `define/`、`requirements/` 中的文档。
>
> 前置：
> - **标准通道**：`plan/to-do/v{N}/` 目录下已有 Story Plan 文件（门禁 3 已通过）
> - **快速通道**：阶段 2 分流决策后，规划Agent 已将方案要点直接传递过来
>
> 贯穿标准：编码规范、设计原则、测试策略已统一定义在 `../methodology.md`，本阶段严格遵循。

## 阶段 4：实施与验证

### 4.0 轨道识别

交付Agent 被激活后，首先判断本次任务的来源：

| 信号 | 轨道 | 流程入口 |
|------|------|---------|
| `plan/to-do/v{N}/` 中存在 Story Plan 文件 | 🔵 标准通道 | 进入 4.1 冲突检查 |
| 用户直接指派变更，`plan/to-do/` 中无对应 Plan | 🟢 快速通道 | 进入快速通道流程（见下方） |
| 用户提到"上次那个小变更"等上下文 | 🟢 快速通道 | 确认后进入快速通道流程 |

> 若不确定轨道，直接向用户确认。

### 🟢 快速通道流程

快速通道适用于已通过阶段 2 分流判定的简单变更。流程从简，但质量门禁不减：

#### F.1 确认范围

1. 回顾阶段 2 的方案要点（影响文件清单、具体改动）
2. 向用户一句话确认即将实施的变更范围
3. 版本号按 PATCH 递增（若用户未指定）

#### F.2 实施

1. 实施前备份受影响的 `data/` 文件到 `data/.backup/`
2. 按方案要点逐项实施代码变更
3. 遵循 `../methodology.md` 设计原则和项目 `CLAUDE.md` 编码规范

**实施后代码自审**（快速通道版）：

| 检查项 | 标准 |
|--------|------|
| 最小变更 | 变更仅限方案范围，无无关改动 |
| 数据安全 | 所有"删除"操作为逻辑删除，无物理删除 |
| 向后兼容 | 新增字段有默认值；存量数据结构未破坏 |
| 一致性 | `define/` 定义、`data/` 数据、源码三者一致 |

#### F.3 定向验证

1. 运行阶段 1 定义的受影响测试用例
2. 确认全部通过（0 失败）
3. 若未通过：定位并修复，重新运行直到全部通过

#### F.4 冒烟测试

运行项目全量测试套件。必须 100% 通过。

若未通过：
1. 根据失败信息排查
2. 修复后重新运行直到全部通过
3. 若 1 小时内无法修复，执行回滚（`git checkout -- <源码文件>` + 从 `data/.backup/` 还原数据）

#### F.5 进入阶段 5

快速通道的阶段 4 完成后（冒烟测试通过），进入阶段 5。阶段 5 流程与标准通道相同（文档同步、变更记录、版本发布说明更新、Git 提交、回顾）。

### 🔵 标准通道：按 Release Version 循环

以下流程对每个 Release Version 执行一遍，从 v1 开始逐个完成。

### 4.1 冲突检查

检索当前版本包含的 Story Plan，分析每个 Plan 涉及的产出文件，判断是否存在写入冲突：

1. **并集分析** — 收集当前版本所有 Story 的文件变更列表，取并集
2. **冲突检测** — 检查是否有多个 Story 修改同一文件：
   - ✅ 无冲突 → 所有 Story 可并行实施
   - ⚠️ 有冲突 → 标注冲突文件，评估冲突严重程度

冲突严重程度：

| 严重程度 | 条件 | 处理方式 |
|---------|------|---------|
| **轻微** | 多 Story 修改同一文件不同函数/区域 | 可并行，最后一次性合入 |
| **中度** | 多 Story 修改同一函数/区域相邻代码 | 串行执行，后者在前者基础上修改 |
| **严重** | 多 Story 修改同一函数/区域同一逻辑 | 合并为一个 Story，或拆分文件 |

3. **依赖确认** — 标注 Story 间依赖关系（依赖方需等待被依赖方完成）
4. 将冲突分析告知用户，给出推荐执行方案，由用户决定

### 4.2 执行排序

基于冲突检查结果，排定 Story 执行顺序：

```
执行计划示例：

  并行批次 1: E1-S1（数据结构变更）              ← 无冲突
  并行批次 2: E1-S2（依赖 E1-S1 产出）           ← 串行等待
  并行批次 3: E2-S1 + E2-S2（互不冲突、无依赖）   ← 并行执行
```

- **并行**：文件变更集合互不相交且无逻辑依赖的 Story，同时启动执行
- **串行**：写入同一文件或存在产出物依赖的 Story，按依赖顺序执行

将执行顺序告知用户并确认。

### 4.3 实施

按照用户确认的执行顺序，逐个或并行执行 Story。

**实施前**：备份受影响的 `data/` 文件到 `data/.backup/`，以便回滚。

**实施步骤**：
1. 按 Story Plan 的子任务清单逐项实施代码变更
2. 遵循 `CLAUDE.md` 定义的编码规范
3. 遵循设计原则（最小变更、数据安全、向后兼容、一致性）

**实施后代码自审**（每个 Story 完成后执行）：

| 检查项 | 标准 |
|--------|------|
| 最小变更 | 变更仅限子任务范围，无无关改动 |
| 数据安全 | 所有"删除"操作为逻辑删除，无物理删除代码 |
| 向后兼容 | 新增字段有默认值；存量数据结构未破坏 |
| 错误处理 | 异常输入有校验，错误信息遵循项目约定格式 |
| 一致性 | `define/` 定义、`data/` 数据、源码三者一致 |

### 4.4 定向验证

每个 Story 实施完成后，立即执行定向验证：

1. 运行该 Story 影响范围内的测试用例（Plan 文件中列出的测试用例编号）
2. 确认全部通过（0 失败）

若定向验证未通过：
- 根据失败信息定位并修复
- 重新运行定向验证，直到全部通过
- **禁止带着测试失败进入下一个 Story**

### 4.5 Story 完成

定向验证通过后：
1. 将 Plan 文件从 `plan/to-do/v{N}/` 移动到 `plan/done/v{N}/`
2. 标记该 Story 为完成

### 4.6 版本冒烟测试（质量门禁）

当前版本所有 Story 都完成且 Plan 文件全部移动到 `plan/done/v{N}/` 后，执行全量冒烟测试：

运行项目定义的全量测试套件（具体命令见项目 `CLAUDE.md`）。

冒烟测试是**版本质量门禁**，必须满足：
- 全量测试用例 **100% 通过**
- 0 个失败，0 个错误

若未通过：
1. 根据失败信息排查（可能是本版本变更引起的回归）
2. 修复后重新运行，直到全部通过
3. 若 1 小时内无法修复，触发回滚方案（见 4.7）

### 4.7 回滚（如需）

若冒烟测试失败且在合理时间内无法修复，执行回滚：

1. **代码回滚**：`git checkout -- <源码文件>`（丢弃源码变更）
2. **数据回滚**：从 `data/.backup/` 覆盖还原 `data/` 目录
3. **重新评估**：回滚后重新分析问题根因，在下一个版本中修复
4. **记录失败**：在 `change-log/` 中记录本次回滚（版本号、失败原因、回滚步骤）

## 阶段 5：记录与提交

阶段 4 全部完成后（冒烟测试通过），执行以下步骤完成版本发布。以下流程适用于**两条轨道**，差异处标注。

### 5.1 文档同步

- **`CLAUDE.md`** — 更新项目文档：目录结构（如有新增文件/目录）、数据模型（如有字段变更）、命令/API 参考（如有新增入口）

### 5.2 变更记录

在 `change-log/` 创建变更记录，命名格式：`YYYY-MM-DD-v{版本号}-{简短描述}.md`

变更记录模板：

```markdown
# v{版本号}: {简短描述}

**日期**: YYYY-MM-DD
**迭代**: {Goal 描述}

## 变更内容
- {变更点 1}
- {变更点 2}

## 质量指标
| 指标 | 结果 |
|------|------|
| 测试通过率 | {N}/{N} (100%) |
| 受影响 Story 数 | {N} |
| 定向验证 | 全部通过 |

## 回顾
- ✅ {做得好的点}
- ⚠️ {摩擦点}
- 🔧 {改进建议}（如有）
```

### 5.3 更新版本发布说明

**标准通道**：将阶段 3 创建的 `versions/v{x.y.z}.md` 中「计划中」的发布日期更新为实际日期；确认「影响范围」章节与实际变更一致。

**快速通道**：创建 `versions/v{x.y.z}.md`（PATCH 版本），注明发布日期和变更内容。

### 5.4 Git 提交

创建独立 commit：

1. 使用 `git diff` 审阅所有变更，确认：
   - 变更仅涉及当前版本范围，无其他变更残留
   - 无调试代码、临时文件混入
   - 所有文件变更符合预期
2. 暂存并提交当前版本涉及的全部文件
3. Commit message 格式：`v{版本号}: {简短描述}`
4. 禁止 `--no-verify` 或跳过 hooks

### 5.5 轻量回顾

Git commit 完成后，立即执行轻量回顾（见 `../methodology.md` 持续改进章节）：

1. What went well?
2. What was painful?
3. What to change?

回顾结论写入变更记录末尾。若改进建议涉及方法论本身，立即修订 `../methodology.md` 或相关 Skill 文件。
