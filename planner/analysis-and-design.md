# 需求分析与方案设计

> 迭代开发流程第一、第二步（规划Agent专用）：理解用户需求，完成解决方案设计。
>
> 本文件由规划Agent使用。规划Agent负责阶段 1-3，产出 Plan 文件到 `plan/to-do/`，不修改源码。
>
> 前置：已读取根目录 `CLAUDE.md` 了解最新项目状态。
>
> 贯穿标准：编码规范、设计原则、测试策略已统一定义在 `../methodology.md`，本阶段严格遵循。

---

## 第 0 步：发现（Discovery）

在进入正式需求分析前，先做一次快速可行性评估。此步骤输出不超过 5 行。

1. **影响面初判** — 粗略判断需求涉及的模块（数据结构？业务规则？新功能？UI？）
2. **可行性判断** — 当前技术栈和架构能否支撑？有无硬性阻塞？
3. **破坏性变更预警** — 是否可能破坏已有数据格式或已有功能行为？
4. **ADR 触发判断** — 是否需要创建架构决策记录？（见 `../methodology.md` ADR 触发条件）

若存在明显阻塞或破坏性变更，先告知用户，等待决策后再继续。

## 阶段 1：需求分析

### 1.1 需求澄清

1. 向用户提问，确保完全理解需求。遵循以下原则：
   - **明确说明假设** — 不确定就询问，不猜测
   - **当存在歧义时，询问而不是默默选择**
   - **如果存在更简单的方法，说出来沟通确认**

2. 追问直至覆盖以下维度：
   - **功能边界** — 做什么、不做什么
   - **用户路径** — 谁在什么场景下使用
   - **数据边界** — 涉及哪些字段、实体、枚举值
   - **非功能需求** — 性能约束？数据量级？兼容性要求？

### 1.2 需求分类

将需求填入以下分类矩阵，不遗漏非功能需求：

| 分类 | 示例 | 本需求涉及？ |
|------|------|------------|
| **功能需求** | 新增字段、新增命令/API、新增校验规则 | |
| **数据变更** | 修改数据结构、新增枚举值、数据迁移 | |
| **业务规则** | 修改编号规则、修改校验逻辑 | |
| **非功能需求** | 性能约束、兼容要求、数据量级 | |
| **约束条件** | 依赖约束、向后兼容要求 | |

### 1.3 变更类型判定

| 变更类型 | 特征 | 影响面 |
|---------|------|--------|
| **数据结构变更** | 增删改字段、新增实体、修改枚举值 | `define/` + `data/` + 源码 |
| **业务规则变更** | 修改编号规则、校验逻辑、操作约束 | 源码 + `define/`（如有约束文档化） |
| **新增操作** | 新的功能入口、新的查看维度 | 源码 + 项目操作文档 |
| **组合变更** | 同时涉及以上多类 | 叠加影响面 |

### 1.4 风险识别

主动识别两类风险，记录到需求文档：

| 风险类型 | 关注点 | 示例 |
|---------|--------|------|
| **数据风险** | 是否涉及数据迁移？存量数据是否有默认值？ | 新增必填字段，已有数据该字段为空 |
| **兼容性风险** | 是否改变已有功能行为？是否改变已有数据格式？ | 修改编号规则导致历史数据不符合新规则 |

风险等级与响应策略见 `../methodology.md` 风险管理框架。

### 1.5 验收标准定义

为本次需求定义验收标准，使用 **Given-When-Then** 格式：

```
场景：{场景名称}
  Given {前置条件}
  When  {触发操作}
  Then  {预期结果}
```

至少覆盖：一个正向场景 + 一个边界/异常场景。

### 1.6 文档更新

与用户确认需求内容和验收标准后，更新以下文档：

- **`requirements/requirements.md`** — 更新需求文档，同步更新「修订记录」章节
- **`requirements/scenario.md`** — 新增/修改业务或运维场景（编号延续）
- **项目操作文档** — 如有新增操作，补充操作流程（如项目有 `user-manual.md` 或 README 等）
- **`testing/test-case.md`** — 新增测试用例（编号对应场景编号；正向场景 + 边界/异常场景）

## 阶段 2：解决方案设计

### 2.1 目标对齐

评审解决方案是否与用户的需求目标一致。回答：此方案是否用最简单的路径满足了验收标准？

### 2.2 逐层设计

按以下顺序做详细设计，由抽象到具体：

#### 第 1 层：领域定义（`define/`）

- 更新数据结构定义（markdown 文档）
- 新增字段标注类型、必填/可选、默认值
- 新增实体标注所有字段和关联关系
- 枚举值变更标注新增值和废弃值（废弃值仅标注，不删除）

#### 第 2 层：数据层（`data/`）

- **`data/enum-dictionary.json`** — 如有枚举值变更，更新字典
- **`data/*` 业务数据文件** — 如有数据结构变更，确保存量数据与新结构兼容（新增字段补充默认值）

#### 第 3 层：代码层（源码目录）

- 遵循 `CLAUDE.md` 定义的编码规范和依赖约束
- 新功能遵循现有代码组织模式（命令结构、API 路由、函数命名等）
- 所有写操作保留校验逻辑
- 错误信息遵循项目约定的格式
- 考虑边界情况：空数据、重复数据、格式错误输入

### 2.3 影响分析

列出受影响文件清单，标注变更类型：

| 文件 | 变更类型 | 具体变更 |
|------|---------|---------|
| `define/*.md` | 修改/新增 | ... |
| `data/enum-dictionary.json` | 修改/不变 | ... |
| `data/*` 业务数据 | 修改/不变 | ... |
| 源码文件 | 修改 | ... |
| 项目操作文档 | 修改/不变 | ... |
| `testing/test-case.md` | 已在阶段 1 更新 | ... |

### 2.4 ADR 创建（如需）

如方案涉及 ADR 触发条件（见 `../methodology.md`），按模板创建到 `define/adr/`。

### 2.5 方案确认

将解决方案和影响分析告知用户，获得确认。

## 阶段 2 出口：分流决策

门禁 2 全部通过后，并非所有变更都需要进入阶段 3。先判断变更去向。

### 分流判断流程

```
门禁 2 通过
    │
    ▼
 用户要求立即实施？
    │
    ├── 否 ──▶ 📥 需求池（记录 backlog 条目，暂不实施）
    │
    └── 是
        │
        ▼
    快速通道条件全部满足？
    ├─ ✅ 变更文件数 ≤ 2
    ├─ ✅ 无数据迁移
    ├─ ✅ 无新实体
    └─ ✅ 无破坏性变更
        │
        ├── 全部满足 ──▶ 🟢 快速通道（跳过阶段 3，直接进入阶段 4）
        │
        └── 任一项不满足 ──▶ 🔵 标准通道（进入阶段 3）
```

### 快速通道条件详解

| 条件 | 检查方法 | 不满足示例 |
|------|---------|----------|
| 变更文件数 ≤ 2 | 统计阶段 2 影响分析清单中源码文件数 | 改 3 个命令文件 |
| 无数据迁移 | 确认不改已有业务数据文件的字段结构 | 给 contracts.json 所有条目加字段 |
| 无新实体 | 确认不新增 `define/` 下的实体定义文件 | 新增供应商实体 |
| 无破坏性变更 | 确认不改变已有 API/命令签名或数据格式 | 修改命令参数名 |

### 各去向后续动作

**📥 需求池**：
1. 按 `../methodology.md` 需求池条目格式，将当前分析结果写入 `requirements/backlog.md`
2. 状态标记为 `refined`（已完成分析，待排期）
3. 告知用户条目已存入需求池，后续可随时选取
4. 本次流程结束

**🟢 快速通道**：
1. 告知用户：本变更满足快速通道条件，将跳过版本计划直接实施
2. 将方案要点和受影响文件清单传递给交付Agent（交付Agent 从 `../deliverer/implementation.md` 快速通道入口开始）
3. 版本号按 PATCH 递增（由交付Agent 在阶段 5 确认）
4. 规划Agent 本次工作完成

**🔵 标准通道**：
1. 告知用户：本变更需进入版本计划
2. 扫描 `requirements/backlog.md` 中 `ready` 条目，询问用户是否本次一起纳入
3. 继续进入「制订方案实施版本计划」（见 `../planner/version-planning.md`）
