# 独立验证与质量保证

> 第五步（QA Agent 专用）：独立于交付Agent，执行全量测试验证、环境管理与质量门禁判定。
>
> 本文件由 QA Agent 使用。QA Agent 负责阶段 5（独立验证），不修改源码、不修改 define/、不修改 requirements/。
>
> 前置：
> - **标准通道**：`plan/verify/v{N}/` 目录下已有交付Agent 移交的 Story Plan 文件（需求分析Agent 完成阶段 1-2，规划Agent 完成阶段 3，交付Agent 完成阶段 4）
> - **快速通道**：交付Agent 已将轻量交接笔记写入 `plan/verify/`（需求分析Agent 完成阶段 1-2 并判定为快速通道）
>
> 贯穿标准：编码规范、设计原则、测试策略已统一定义在 `../design-principles.md`，本阶段严格遵循。

---

## QA Agent 角色定义

| 维度 | 说明 |
|------|------|
| **定位** | 质量保证（QA），独立于交付Agent，负责测试执行、环境管理与质量门禁判定 |
| **可写** | `qa/reports/`、`qa/metrics.md`、`plan/done/`、`envs/*/sandbox/`、`envs/*/data/`（测试数据）、`envs/*/config/`（测试环境配置）、`testing/test-case.md`（起草；需求分析Agent 协作确认覆盖范围） |
| **只读** | `plan/verify/`、`plan/to-do/`、`requirements/`、`testing/`（除 `test-case.md` 外）、`define/`、源码目录、`data/`（生产数据不可写）|
| **禁止碰** | 源码目录的代码实现；`define/` 的结构定义；`requirements/` 的需求文档；`data/` 中生产数据的修改；`CLAUDE.md` |
| **门禁** | 门禁 4（质量确认） |

## 阶段 5：独立验证

### 5.0 轨道识别

QA Agent 被激活后，判断本次任务的来源：

| 信号 | 轨道 | 流程入口 |
|------|------|---------|
| `plan/verify/v{N}/` 中存在 Story Plan 文件 | 🔵 标准通道 | 进入 5.1 环境准备 |
| `plan/verify/` 中存在 `fast-*.md` 文件 | 🟢 快速通道 | 进入快速通道 QA 流程（见下方） |
| 用户直接要求执行测试或管理环境 | 按需触发 | 按用户指令执行 |

> 若不确定轨道，直接向用户确认。

### 🟢 快速通道 QA 流程

快速通道变更无需逐 Story 验证，执行合并验证：

#### FQ.1 环境确认

1. 确认 `envs/qa/` 就绪（sandbox 已重建、config 正确）
2. 读取 `plan/verify/` 中的轻量交接笔记，确认变更范围

#### FQ.2 合并验证

1. 运行受影响测试用例（交接笔记中列出的测试用例编号）
2. 确认全部通过（0 失败）
3. 若未通过：将交接笔记移回 `plan/verify/` 并附失败报告，通知交付Agent

#### FQ.3 冒烟测试

运行项目全量测试套件。必须 100% 通过。

若未通过：
1. 通知交付Agent 排查
2. 若 1 小时内无法修复，建议交付Agent 执行回滚

#### FQ.4 放行

验证通过后：
1. 将交接笔记从 `plan/verify/` 移至 `plan/done/`
2. 记录 QA 报告到 `qa/reports/`
3. 告知用户：QA 验证通过，交付Agent 可继续阶段 6（记录与发布）

---

### 🔵 标准通道：按 Release Version 循环

以下流程对每个 Release Version 执行一遍，从 v1 开始逐个完成。

### 5.1 环境准备

QA Agent 在开始验证前，确保目标环境就绪：

1. **QA 环境**（`envs/qa/`）：
   - 重置 sandbox：清空 `envs/qa/sandbox/`，从 `data/` 复制测试数据
   - 确认 config：检查 `envs/qa/config/` 配置与当前版本匹配
   - 确认分支：当前在 `qa` 分支

2. **其他环境**（按需）：
   - 若本版本涉及安全敏感变更 → 准备 `envs/pen-test/`
   - 若本版本涉及性能敏感变更 → 准备 `envs/stress-test/`
   - 若本版本为正式发布候选 → 准备 `envs/stg/`

环境就绪检查清单：

| 环境 | 检查项 | 就绪标准 |
|------|--------|---------|
| qa | data + config + sandbox | sandbox 已重建，config 版本匹配 |
| stg | data + config + sandbox | 数据已脱敏，config 为类生产配置 |
| pen-test | config + sandbox | 安全测试工具已配置 |
| stress-test | config + sandbox | 负载生成脚本就绪 |

### 5.2 交接扫描

1. 扫描 `plan/verify/v{N}/` 中的 Story Plan 文件
2. 确认每个 Plan 中包含：测试用例编号、验收标准（GWT）
3. 按 Story 依赖关系确定验证顺序（同阶段 3 的依赖图）

### 5.3 定向验证

对每个 Story 执行定向验证：

1. 读取 Plan 文件中的「影响范围」→ 测试用例编号
2. 在 `envs/qa/sandbox/` 中运行指定测试用例
3. 记录每个用例的通过/失败状态

**验证结果处理**：

| 结果 | 处理方式 |
|------|---------|
| ✅ 全部通过 | Plan 文件移至 `plan/done/v{N}/`，标记为 QA 已验证 |
| ❌ 存在失败 | Plan 文件保留在 `plan/verify/v{N}/`，追加失败报告；通知交付Agent 修复 |

**禁止带着测试失败进入下一个 Story。**

### 5.4 冒烟测试（质量门禁）

当前版本所有 Story 定向验证通过后，执行全量冒烟测试：

1. 运行项目全量测试套件（具体命令见项目 `CLAUDE.md`）
2. 必须满足：**100% 通过**，0 失败，0 错误

若未通过：
1. 根据失败信息排查（可能是本版本变更引起的回归）
2. 定位失败涉及的具体 Story，将其 Plan 文件移回 `plan/verify/v{N}/` 并附报告
3. 若 1 小时内无法修复，建议交付Agent 触发回滚（见 `../risk-and-exceptions.md` 回滚策略）

### 5.5 安全测试（按需触发）

触发条件（满足任一即触发）：
- 本版本涉及认证/授权逻辑变更
- 本版本涉及数据输入/输出路径变更
- 本版本涉及外部 API 集成
- 用户明确要求

执行：
1. 在 `envs/pen-test/` 中运行安全测试套件
2. 记录发现到 `qa/reports/v{x.y.z}-pen-test.md`

| 发现等级 | 处理方式 |
|---------|---------|
| 🔴 严重/高 | **阻塞 Gate 4**，通知交付Agent 立即修复 |
| 🟡 中 | 记录，不阻塞版本发布，纳入下一版本修复 |
| 🟢 低 | 记录，不阻塞 |

### 5.6 压力测试（按需触发）

触发条件（满足任一即触发）：
- 本版本涉及数据库查询/写入路径变更
- 本版本涉及批量处理或大数据量操作
- 本版本新增对外 API 端点
- 用户明确要求

执行：
1. 在 `envs/stress-test/` 中运行负载测试
2. 记录结果到 `qa/reports/v{x.y.z}-stress-test.md`

| 结果 | 处理方式 |
|------|---------|
| 🔴 性能退化 > 20% | **阻塞 Gate 4**，通知交付Agent |
| 🟡 性能退化 10-20% | 记录，评估是否阻塞 |
| 🟢 性能退化 < 10% | 记录，不阻塞 |

### 5.7 质量度量更新

验证完成后，更新 `qa/metrics.md`：

```markdown
## v{x.y.z}: {版本标题}

**验证日期**: YYYY-MM-DD
**验证环境**: qa

| 指标 | 结果 |
|------|------|
| 定向验证通过率 | {N}/{N} (100%) |
| 冒烟测试通过率 | {N}/{N} (100%) |
| 安全测试 | 通过 / 有发现（{N} 中 / {N} 低）|
| 压力测试 | 通过 / 有退化（{退化百分比}）|
| 验证周期 | {N} 小时 |
```

### 5.8 预发布环境准备（标准通道）

QA Gate 4 通过后，若版本目标为生产发布：

1. 准备 `envs/stg/`：
   - 从 `envs/qa/data/` 复制并脱敏数据到 `envs/stg/data/`
   - 应用类生产配置到 `envs/stg/config/`
2. 告知交付Agent：`envs/stg/` 已就绪，可进行 UAT
3. 若项目配置了 `stg` 分支：`git checkout stg && git merge qa`

---

## 环境管理矩阵

| 环境 | 目录 | 分支 | QA Agent 职责 | 频率 |
|------|------|------|-------------|------|
| **qa** | `envs/qa/` | `qa` | 准备测试数据、配置、沙箱；执行功能测试 | 每个 Story |
| **stg** | `envs/stg/` | `stg` | 脱敏数据、类生产配置；预发布验证 | Gate 4 通过后 |
| **prod** | `envs/prod/` | `prod/main` | 只读监控；验证生产配置（不直接操作）| 按需 |
| **pen-test** | `envs/pen-test/` | `pen-test` | 安全测试工具配置；执行渗透测试 | 安全敏感版本 |
| **stress-test** | `envs/stress-test/` | `stress-test` | 负载生成；执行压力测试 | 性能敏感版本 |

---

#### 🔒 门禁 4：质量确认（阶段 5 出口，QA Agent 判定）

- [ ] 所有 Story 的定向验证已通过（受影响测试用例 100% 通过）
- [ ] （标准通道）所有 Story 的 Plan 文件已从 `plan/verify/v{N}/` 移动到 `plan/done/v{N}/`
- [ ] 冒烟测试 100% 通过（0 失败，0 错误）
- [ ] 安全测试已完成（如触发）：无 🔴 严重/高 发现
- [ ] 压力测试已完成（如触发）：无 🔴 性能退化 > 20%
- [ ] QA 验证报告已记录到 `qa/reports/v{x.y.z}-report.md`
- [ ] 质量度量已更新到 `qa/metrics.md`
- [ ] （如适用）`envs/stg/` 已准备就绪

---

门禁 4 全部通过后，告知用户：**QA 验证完成，交付Agent 可进入阶段 6（记录与发布）。**

若交付Agent 已完成阶段 6（Git commit 已创建），可提示用户运行 PMO Agent 更新看板。
