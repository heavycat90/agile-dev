# 制订方案实施版本计划

> 迭代开发流程第三步（规划Agent专用，标准通道）：扫描需求池，选取条目，将解决方案拆解为可独立交付的 Story，按 Release Version 组织版本计划。
>
> 本文件由规划Agent使用。规划Agent负责阶段 1-3，产出 Plan 文件到 `plan/to-do/`，不修改源码。
>
> 前置：阶段 2 分流决策已完成，判定为「标准通道」。
>
> 贯穿标准：编码规范、设计原则、测试策略已统一定义在 `../design-principles.md`，本阶段严格遵循。

---

## 阶段 3：制订方案实施计划

### 3.0 从需求池选取

在拆解当前需求之前，先扫描 `requirements/backlog.md` 中状态为 `ready` 的条目。这些是已经过完整分析、待排期的需求。

1. **扫描 backlog** — 读取 `requirements/backlog.md`，列出所有 `状态: ready` 的条目
2. **匹配关联** — 检查 ready 条目中是否有与当前需求关联的需求（如同一业务域、存在依赖关系等）
3. **提议合并** — 向用户提议：
   - 当前需求单独进入版本计划
   - 或与关联的 backlog ready 条目合并为同一版本
   - 给用户选择权，不自动决定
4. **确认选取** — 用户确认后，将选中条目标记为 `done`（注明版本号），进入 3.1 拆解

> 若 backlog 中无 ready 条目，或用户选择不合并，则仅以当前需求进入 3.1。

### 3.1 Goal → Epic → Story 拆解

将解决方案按 Agile 方法论逐级拆解：

#### Goal

本次迭代要达成的总体目标，即用户需求的核心意图。一句话表述。

#### Epic

一个完整的业务流程或业务功能。拆分标准：
- 能代表一个独立、完整的业务能力
- 每个 Epic 在概念上独立于其他 Epic，不共享核心业务逻辑

#### Story

Epic 内某个角色的完整 E2E 业务场景。拆分标准：
- 从用户视角出发，描述一个端到端的操作流程
- 每个 Story 是一个子目标，可独立实施、独立验证、独立交付
- 每个 Story 对应 `requirements/scenario.md` 中的一个或多个场景
- 每个 Story 对应 `testing/test-case.md` 中对应的测试用例

#### 示例拆解

```
Goal: 用户管理支持角色与权限控制
  │
  ├── Epic 1: 用户角色管理
  │     ├── Story 1: 创建用户时分配角色
  │     └── Story 2: 编辑用户时修改角色
  │
  └── Epic 2: 权限校验
        ├── Story 3: 基于角色的功能访问控制
        └── Story 4: 无权限操作的错误提示
```

### 3.2 Story 估算

按复杂度估算每个 Story，不使用人天（个人项目无法校准）：

| 复杂度 | 特征 | 建议上限 |
|--------|------|---------|
| 🟢 **小** | 单一文件变更，≤ 1 个新增功能点/字段，无数据迁移 | 2 小时内 |
| 🟡 **中** | 多文件变更，1-2 个新增功能点/字段，可能涉及少量存量数据处理 | 半天内 |
| 🔴 **大** | 跨层变更，≥ 3 个新增功能点/字段，涉及数据迁移或规则变更 | 应拆分为多个小/中 Story |

> 若出现 🔴 大 Story，优先考虑是否有进一步拆分的可能。

### 3.3 依赖关系分析

分析 Story 之间的依赖关系，绘制依赖图：

```
ASCII 依赖关系图示例：

  E1-S1（角色分配）
    │
    ├──▶ E1-S2（修改角色） 依赖 E1-S1 的数据结构
    │
    └──▶ E2-S1（访问控制） 依赖 E1-S1 的存储字段
          │
          └──▶ E2-S2（错误提示） 依赖 E2-S1 的校验逻辑
```

标注规则：
- `──▶` 表示依赖方向（箭头指向被依赖方）
- 循环依赖应被识别并解除（拆分共享逻辑到独立 Story）
- 无连线的 Story 可并行实施

### 3.4 Story 细化

对每个 Story 输出以下内容：

```markdown
### {Epic序号}-{Story序号}: {标题}

**复杂度**: 小 / 中 / 大
**依赖**: {依赖的 Story 编号} / 无

**验收标准** (Given-When-Then):
- 场景 1: {正向场景}
- 场景 2: {边界/异常场景}

**影响范围**:
- 场景: S-NN, S-MM
- 测试用例: TC-NN, TC-MM

**子任务清单**:
1. {具体任务描述}
2. {具体任务描述}
...

**定向验证子任务**:
- [ ] 运行测试用例 TC-NN、TC-MM，全部通过
```

### 3.5 Release Version 划分

基于以下维度评估是否需要分多个版本：

| 评估维度 | 单版本条件 | 多版本条件 |
|---------|-----------|-----------|
| Story 数量 | ≤ 2 个 | ≥ 3 个 |
| 改动点总数 | ≤ 5 处 | > 5 处 |
| 风险等级 | 全部 🟢 | 存在 🟡 或 🔴 |
| 依赖链深度 | ≤ 2 层 | > 2 层 |

每个版本建议包含 **1-3 个 Story**，上限 3 个（控制失败半径）。

#### 风险驱动优先级

排列 Story 的 Release Version 归属时，优先纳入高风险 Story：

1. 🔴 高风险 Story → 放入最早的版本，尽早验证
2. 依赖链深度 → 被依赖的 Story 放入更早版本
3. 业务价值 → 用户最关心的 Story 优先

### 3.6 回滚方案

为每个 Release Version 预定义回滚方案：

```markdown
**回滚方案**:
- 代码回滚: `git revert {commit_hash}`
- 数据备份: 实施前备份 `data/` 到 `data/.backup/`，回滚时覆盖还原
- 回滚触发条件: 冒烟测试失败且 1 小时内无法修复
```

### 3.7 用户确认

将拆分方案、依赖关系、版本划分告知用户并确认。尤其是：
- Story 是否覆盖了所有验收场景
- 版本划分是否符合用户期望
- 回滚方案是否可接受

### 3.8 输出 Plan 文件

用户确认后，按 Release Version 创建目录并输出 Plan 文件：

```
plan/to-do/
├── v1/
│   ├── E1-S1-{简短描述}.md
│   └── E1-S2-{简短描述}.md
└── v2/
    └── E2-S1-{简短描述}.md
```

命名格式：`{Epic序号}-{Story序号}-{简短描述}.md`

每个 Plan 文件包含：该 Story 的完整细化内容（验收标准、影响范围、子任务清单、定向验证子任务、风险信息、回滚方案）。

### 3.9 更新版本路线图与发布说明

Plan 文件输出完成后，为本次迭代涉及的所有 Release Version 创建/更新版本文件：

#### 3.9.1 更新 `versions/roadmap.md`

路线图文件提供所有版本的总览视图。按时间倒序排列，最新版本在最前。

`roadmap.md` 格式：

```markdown
# 产品版本路线图

## v{x.y.z} — {简短描述}（当前）
**发布日期**: YYYY-MM-DD
**类型**: MAJOR / MINOR / PATCH
**核心特性**:
- {特性 1}
- {特性 2}

## v{x.y.z} — {简短描述}
**发布日期**: YYYY-MM-DD
**类型**: MINOR
**核心特性**:
- {特性 1}
...
```

> 首次使用时创建该文件，后续迭代在文件顶部插入新版本条目。

#### 3.9.2 创建 `versions/v{x.y.z}.md`

为每个 Release Version 创建独立的发布说明文件，描述该版本的主要更新内容。

`v{x.y.z}.md` 格式：

```markdown
# v{x.y.z}: {版本标题}

**发布日期**: YYYY-MM-DD
**版本类型**: MAJOR / MINOR / PATCH
**关联 Epic**: {Epic 编号和标题}

## 更新内容

### 新增
- {新增功能/命令/字段}

### 变更
- {已有行为的修改}

### 修复
- {Bug 修复（如有）}

### 影响范围
| 层面 | 变更 |
|------|------|
| define/ | {数据结构定义变更} |
| data/ | {数据变更} |
| 源码 | {代码变更} |
| 测试用例 | {新增/修改的测试用例编号} |

## 升级说明
{如有破坏性变更或需要手动操作，在此说明；若为纯新增功能，写「无需额外操作」}
```

> 阶段 3 创建此文件时，发布日期暂填「计划中」；阶段 5 发布时更新为实际日期。
