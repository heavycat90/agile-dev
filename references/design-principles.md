# 设计原则与编码规范

> 本方法论的核心价值观与贯穿所有阶段的编码标准。所有 Agent 实施时以此为唯一标准。

## 核心哲学

五条核心价值观贯穿整个迭代生命周期，所有决策和设计以此为锚：

| 原则 | 含义 | 反模式 |
|------|------|--------|
| **最小变更** | 只改受影响的部分，不做无关重构 | "顺便重构一下"的冲动 |
| **数据安全** | 逻辑删除原则不可破坏，永不物理删除 | `DELETE` 语句、`rm` 数据文件 |
| **向后兼容** | 新增字段有默认值，不破坏已有数据结构 | 新增必填字段却不给默认值 |
| **一致性** | 定义层 → 数据层 → 代码层 → 测试层 四层同步 | 改了代码忘了更新文档 |
| **可追溯** | 需求 → 场景 → Story → 代码 → 测试 → 发布 全链路可追踪 | "这个改动对应哪个需求来着？" |

## 编码规范

编码规范由各项目在根目录 `CLAUDE.md` 中定义。本方法论不硬编码特定技术栈规则。

项目 `CLAUDE.md` 应至少声明：
- **编程语言与版本** — 如 Python 3.12+、Node.js 20+ 等
- **依赖约束** — 如"纯标准库"、"允许的第三方包"等
- **入口文件** — 项目的主入口路径
- **命名规范** — 字段命名、函数命名、文件命名约定
- **输出格式** — 用户界面的语言和格式约定
- **错误处理** — 错误信息的格式和退出方式

## 设计原则

- **最小变更** — 只改受影响的部分，不做无关重构。一个 PR 解决一个问题
- **数据安全** — 逻辑删除原则不可破坏，不做物理删除。"删除"操作只改状态字段
- **向后兼容** — 新增字段必须有默认值，不破坏已有数据结构。存量数据能正常读取
- **一致性** — 定义层 → 数据层 → 代码层 → 测试层 四个层面保持同步，任一变更触发关联更新

## 测试策略

| 层级 | 说明 | 执行者 | 触发时机 |
|------|------|--------|---------|
| **定向验证** | 执行当前 Story 涉及的测试用例（`testing/test-case.md` 中对应编号） | QA Agent | 交付Agent 移交 Story 后 |
| **冒烟测试** | 运行全量测试套件 | QA Agent | 当前版本所有 Story 定向验证通过后 |
| **回归验证** | 用户手动验证受影响场景的实际行为 | 用户/PO | 冒烟测试通过后 |
| **环境级验证** | 在特定环境中运行安全/压力测试套件 | QA Agent | 触发条件满足时（安全/性能敏感变更） |

测试通过标准：
- 定向验证：受影响用例 **100% 通过**
- 冒烟测试：全量用例 **100% 通过**（0 失败，0 错误）
- 回归验证：至少一个正向场景和边界场景手动确认
- 环境级验证：安全测试无 🔴 严重/高 发现；压力测试无 🔴 性能退化 > 20%

## 沙箱隔离（硬规则）

> **任何涉及数据写入的验证操作，必须在沙箱环境执行，禁止对生产数据文件进行手动测试。**

此规则适用于所有角色（需求分析Agent、规划Agent、交付Agent、QA Agent、开发者手动验证）。

沙箱位于各环境的独立目录下（`envs/{env}/sandbox/`），与生产 `data/` 物理隔离：

| 环境 | 沙箱路径 | 用途 |
|------|---------|------|
| qa | `envs/qa/sandbox/` | 功能测试沙箱 |
| stg | `envs/stg/sandbox/` | 预发布验证沙箱 |
| prod | `envs/prod/sandbox/` | 生产只读沙箱 |
| pen-test | `envs/pen-test/sandbox/` | 安全测试沙箱 |
| stress-test | `envs/stress-test/sandbox/` | 压力测试沙箱 |

| 验证类型 | ✅ 正确做法 | ❌ 禁止 |
|---------|------------|--------|
| **API / 表单验证** | 使用项目提供的 `--sandbox` 参数启动隔离 API 实例 | 对生产 API 端口直接执行写入操作 |
| **CLI 验证** | 运行 `testing/test-runner.py`（自动沙箱隔离） | 直接执行 `scripts/mgr.py` 命令做临时验证 |
| **数据文件** | 在 `envs/{env}/sandbox/` 中操作测试数据 | 修改 `data/` 目录下的生产 JSON 文件 |

违规即视为流程事故，需清理生产数据中的测试残留并记录回顾。
