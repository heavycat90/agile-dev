# 设计原则与编码规范

> 本方法论的核心价值观与贯穿所有阶段的编码标准。所有 Agent 实施时以此为唯一标准。

## 核心哲学

五条核心价值观贯穿整个迭代生命周期，所有决策和设计以此为锚：

| 原则 | 含义 | 反模式 |
|------|------|--------|
| **最小变更** | 只改受影响的部分，不做无关重构。一个 PR 解决一个问题 | "顺便重构一下"的冲动；PR 中混入不相关改动 |
| **数据安全** | 逻辑删除原则不可破坏，永不物理删除。"删除"操作只改状态字段 | `DELETE` 语句、`rm` 数据文件 |
| **向后兼容** | 新增字段有默认值，不破坏已有数据结构。存量数据能正常读取 | 新增必填字段却不给默认值；修改已有字段的语义 |
| **一致性** | 定义层 → 数据层 → 代码层 → 测试层 四层同步，任一变更触发关联更新 | 改了代码忘了更新文档；define 与 data 字段不一致 |
| **可追溯** | 需求 → 场景 → Story → 代码 → 测试 → 发布 全链路可追踪 | "这个改动对应哪个需求来着？" |

## 编码规范

编码规范由各项目在根目录 `project-basic.md` 中定义。本方法论不硬编码特定技术栈规则。

项目 `project-basic.md` 应至少声明：
- **编程语言与版本** — 如 Python 3.12+、Node.js 20+ 等
- **依赖约束** — 如"纯标准库"、"允许的第三方包"等
- **入口文件** — 项目的主入口路径
- **命名规范** — 字段命名、函数命名、文件命名约定
- **输出格式** — 用户界面的语言和格式约定
- **错误处理** — 错误信息的格式和退出方式

## 测试策略

| 层级 | 说明 | 执行者 | 触发时机 |
|------|------|--------|---------|
| **定向验证** | 执行当前 Story 涉及的测试用例（`function-testing/test-case.md` 中对应编号） | QA Agent | 交付Agent 移交 Story 后 |
| **冒烟测试** | 运行全量测试套件 | QA Agent | 当前版本所有 Story 定向验证通过后 |
| **回归验证（UAT）** | 用户手动验证受影响场景的实际行为 | 用户/PO | Gate 4 通过后，stg→prod 发布前 |
| **环境验证** | 在特定环境中运行安全/压力测试套件 | QA Agent | 触发条件满足时（安全/性能敏感变更） |

测试通过标准：
- 定向验证：受影响用例 **100% 通过**
- 冒烟测试：全量用例 **100% 通过**（0 失败，0 错误）
- 回归验证：至少一个正向场景和边界场景手动确认
- 环境验证：安全测试无 🔴 严重/高 发现；压力测试无 🔴 性能退化 > 20%

## 沙箱隔离（硬规则）

> **环境之间必须物理隔离。任何涉及数据写入的操作，必须在对应环境内执行，禁止跨环境操作。**

此规则适用于所有角色（需求分析Agent、规划Agent、交付Agent、QA Agent、开发者手动验证）。

环境隔离方式由 `project-basic.md` 中 `branch-management.enabled` 决定：

### 模式 A：目录隔离（`branch-management.enabled = false`）

每个 `envs/{env}/` 目录即为独立沙箱：

| 环境 | 沙箱路径 | 用途 | 写入权限 |
|------|---------|------|---------|
| dev | `envs/dev/` | 开发集成 | 开发活动写入 |
| qa | `envs/qa/` | 功能测试 | 仅 QA 活动写入 |
| stg | `envs/stg/` | 预发布验证 | 只读（由晋升流程写入） |
| prod | `envs/prod/` | 生产环境 | 仅发布流程写入 |
| hotfix | `envs/hotfix/` | 紧急修复 | 仅 Hotfix 活动写入 |
| pen-test | `envs/pen-test/` | 安全测试（`security-testing` 启用时） | 仅安全测试活动写入 |
| stress-test | `envs/stress-test/` | 压力测试（`stress-testing` 启用时） | 仅压力测试活动写入 |

| 验证类型 | ✅ 正确做法 | ❌ 禁止 |
|---------|------------|--------|
| **API / 表单验证** | 在 `envs/qa/` 中启动隔离 API 实例 | 对生产 API 端口直接执行写入操作 |
| **CLI 验证** | 通过项目测试运行器执行（自动指向当前环境） | 直接执行业务命令脚本做临时验证 |
| **数据文件** | 在 `envs/{env}/data/` 中操作对应环境的测试数据 | 修改 `data/` 目录下的生产数据文件 |
| **跨环境** | 每个活动只在对应的 `envs/{env}/` 内写入 | 向非对应环境目录写入数据 |

### 模式 B：分支隔离（`branch-management.enabled = true`）

环境通过 Git 分支隔离，`data/` 和 `config/` 随分支切换：

| 环境 | Git 分支 | 用途 | 写入权限 |
|------|---------|------|---------|
| dev | `dev` | 开发集成 | 开发活动写入 |
| qa | `qa` | 功能测试 | 仅 QA 活动写入 |
| stg | `stg` | 预发布验证 | 只读（由晋升流程写入） |
| prod | `prod` / `main` | 生产环境 | 仅发布流程写入 |
| hotfix | `hotfix` | 紧急修复 | 仅 Hotfix 活动写入 |
| pen-test | `pen-test` | 安全测试（`security-testing` 启用时） | 仅安全测试活动写入 |
| stress-test | `stress-test` | 压力测试（`stress-testing` 启用时） | 仅压力测试活动写入 |

| 验证类型 | ✅ 正确做法 | ❌ 禁止 |
|---------|------------|--------|
| **环境切换** | `git checkout qa` 切换到 QA 环境后再操作 | 在 `prod` 分支上执行测试写入 |
| **API / 表单验证** | 在 `qa` 分支上启动 API 实例 | 在 `prod` 分支上执行写入操作 |
| **CLI 验证** | 切换到 `qa` 分支后通过项目测试运行器执行 | 当前分支为 `prod` 时执行业务命令脚本做临时验证 |
| **数据文件** | 在当前分支的 `data/` 中操作 | 在 `prod` 分支修改数据后合并到其他分支 |
| **跨环境** | 每个活动只在对应分支上执行写入 | 在非对应分支上执行写入操作 |

违规即视为流程事故，需清理污染数据并记录回顾。
