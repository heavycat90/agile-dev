# 项目接入治理

> 新项目或存量项目接入本方法论的治理规则：接入场景分类、前置条件、触发流程、约束与边界。
> 读者是全体 Agent 和用户。
> 详细操作模板见 [`foundations/project-init-template.md`](../foundations/project-init-template.md)。

## 接入场景

本方法论支持三种接入场景，初始化流程因项目状态而异：

| 场景 | 项目状态 | 触发表述示例 |
|------|---------|------------|
| 🆕 **全新项目** | 已有 Git 仓库，目录为空或仅有初始骨架 | "这是新项目叫 X" |
| 🔧 **全新项目（无 Git）** | 尚未执行 `git init`，用户对方法论不熟悉 | "我想建一个新项目"（在普通目录中） |
| 📦 **存量项目接入** | 已有代码、数据、Git 历史，开发进行中 | "把我当前的项目接入方法论" |

三种场景共享同一套治理原则（见下节），差异仅在于初始化的入口步骤。

---

## 治理原则

项目初始化是将一个项目纳入方法论管理的入口。以下规则适用于所有接入场景。

### 接入前提

三条前提全部满足方可进入初始化流程：

- **用户意图明确** — 用户表达了接入本方法论的意图（含上述三种场景的触发表述）
- **项目根目录可写** — 初始化需在目标目录下创建文件和子目录
- **项目身份可识别** — 项目有名称（用于看板标题和报告标识），且根目录路径已确定

> Git 仓库**不是**接入前提。若用户尚未执行 `git init`，由初始化流程引导完成——不应因缺少 Git 仓库而拒绝接入。

### 初始化触发

用户在对话中表达接入意图时触发。若用户表述模糊（如只说"帮我建个项目"而未说明是全新项目还是存量接入），应主动追问澄清。

### 初始化流程（治理视图）

三种场景的流程差异仅在入口步骤，核心路径一致：

```
场景 🆕 全新项目：
  用户触发 → 创建 project-basic.md → 目录初始化 → 就绪

场景 🔧 无 Git：
  用户触发 → git init → 创建 project-basic.md → 目录初始化 → 就绪

场景 📦 存量项目：
  用户触发 → 盘点现有结构 → 创建 project-basic.md（描述现状）→ 目录初始化（非破坏性合并）→ 就绪
```

各步骤说明：

1. **（🔧 专属）git init** — 引导用户完成 `git init`，创建初始 commit（可选但建议）。此步骤完成后流转到标准流程。
2. **（📦 专属）盘点现有结构** — 扫描现有目录树、数据文件、代码入口，作为填写 `project-basic.md` 的依据。此步骤不修改任何文件，仅做读取和记录。
3. **创建 `project-basic.md`** — 用户按模板填写项目元信息。🆕/🔧 场景下是规划未来状态；📦 场景下是**描述既有现实**（目录结构、技术栈、数据模型均如实反映当前项目）。
4. **目录初始化** — 系统根据 `project-basic.md` 中的功能模块开关，创建标准目录和环境目录。
5. **进入就绪状态** — 各 Agent 可正常启动。

### 约束与边界

**所有场景共同约束**：

- **初始化必须在任何 Agent 工作之前完成** — 没有 `project-basic.md` 和标准目录结构，Agent 无法确定项目上下文和工作路径。
- **功能模块开关一经设定不应频繁变更** — `branch-management` 在目录隔离和分支隔离之间切换会引起环境重建成本；`security-testing` 和 `stress-testing` 的开关影响 QA Agent 的测试范围。
- **初始化命令幂等** — 目录创建命令可安全重复执行，不会覆盖已有文件。

**📦 存量项目额外约束**：

- **非破坏性合并** — 标准目录创建在现有项目目录**旁边**，不移动、不覆盖、不删除已有文件和目录。唯一可能冲突的是同名目录（如项目已有 `data/`），此时初始化应仅创建缺失的子目录，不覆盖已有内容。
- **描述现状，不预设未来** — `project-basic.md` 中的目录结构、技术栈、数据模型、关键规则等章节均应反映项目的**当前实际状态**，而非方法论期望的理想状态。这确保 Agent 读取后能正确理解现有代码，而非被误导。
- **版本号尊重历史** — 若项目已有版本号体系（如 `v2.3.1`），初始版本号沿用该值，不强行归零到 `1.0.0`。若项目无版本号体系，从 `1.0.0` 开始。
- **存量数据视为生产数据** — 已有 `data/` 目录中的文件视为生产数据，初始化过程中不修改、不迁移。若方法论要求逻辑删除字段（如 `is_deleted`），存量数据缺少该字段时，由后续需求分析Agent 在第一个版本规划中作为技术债务处理，不在初始化阶段强行补齐。
- **Git 历史完整保留** — 不修改已有 commit 历史，不强制 rebase。初始化产生的文件（`project-basic.md`、标准目录）作为新的 commit 提交。

## 初始化后的状态

初始化完成后，项目具备：
- `project-basic.md`（项目元信息）
- 标准目录结构（`define/`、`data/`、`requirements/`、`plan/`、`qa/`、`pmo/`、`function-testing/` 等）
- 核心 5 环境（`dev`、`qa`、`stg`、`prod`、`hotfix`）
- 可选环境（`pen-test`、`stress-test`，由模块开关控制）

📦 存量项目接入后，以上目录和文件与项目已有内容并存，互不干扰。

此时项目已就绪，可进入需求分析Agent 流程。

---

## 📦 存量项目接入后的首次迭代建议

存量项目接入后，第一个 Release Version 通常面临两类工作：

1. **技术债务清偿** — 存量数据缺少逻辑删除字段、缺少测试用例、代码未遵循设计原则等。这些应以 backlog 条目的形式记录，由规划Agent 纳入版本排期，不与当前业务需求混在一起。
2. **业务需求继续** — 用户接入方法论前的进行中工作，通过需求分析Agent 创建对应 backlog 条目，走标准通道或快速通道继续推进。

建议第一个版本**不追求一次性对齐所有方法论规范**——优先让业务需求流转起来，技术债务逐版本消化。
