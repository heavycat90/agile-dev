# 风险管理、ADR 与异常流程

> 风险识别与响应、架构决策记录、紧急修复与回滚策略、禁止事项。

## 风险管理框架

### 风险等级

| 等级 | 含义 | 响应策略 |
|------|------|---------|
| 🔴 **高** | 可能导致数据丢失、不可逆操作 | 方案必须包含回滚计划；用户必须明确确认 |
| 🟡 **中** | 可能影响已有数据格式或已有功能行为 | 方案中标注缓解措施；加强回归测试 |
| 🟢 **低** | 纯新增功能，不影响已有模块 | 正常流程，无需额外措施 |

### 风险识别触发点

- **需求分析阶段**：识别需求本身的风险（数据迁移？破坏性变更？）——需求分析Agent 负责
- **方案设计阶段**：识别方案实施的技术风险（影响面大？逻辑复杂？）——需求分析Agent 负责
- **版本计划阶段**：识别版本编排风险（Story 间依赖冲突？容量过载？）——规划Agent 负责
- **实施阶段**：识别实施中的意外风险（数据结构冲突？存量数据边界情况？）——交付Agent 负责，发现后应反馈规划Agent，必要时修订 Plan
- **验证阶段**：识别验证中的回归风险（冒烟测试失败？性能退化？安全漏洞？）——QA Agent 负责，发现后通知交付Agent，必要时触发回滚

风险识别结果记录在对应 Plan 文件中，格式：`风险等级 | 风险描述 | 缓解措施`

## 架构决策记录（ADR）

### 触发条件

满足以下任一条件时，必须在 `define/adr/` 目录下创建 ADR：

1. 引入新的设计模式或架构约束（如"引入 Repository 模式隔离数据访问""所有命令统一用装饰器注册"——若项目已有此模式则不触发；判断标准：项目的 `define/` 或 `project-basic.md` 中是否已有此约束的文档记录）
2. 修改编号规则、校验逻辑等核心业务规则
3. 数据模型发生结构性变化（新增实体、字段语义变更）
4. 方案存在两个以上可行路径，需要记录选择理由

### ADR 模板

文件名：`define/adr/YYYY-MM-DD-{简短标题}.md`

```markdown
# ADR: {决策标题}

**日期**: YYYY-MM-DD
**状态**: 提议 / 已采纳 / 已废弃
**决策者**: {角色}

## 背景
{为什么需要做这个决策？上下文是什么？}

## 决策
{选择了什么方案？}

## 备选方案
| 方案 | 优点 | 缺点 |
|------|------|------|
| A: ... | ... | ... |
| B: ... | ... | ... |

## 影响
{这个决策影响了哪些部分？}
```

## 异常流程

### Hotfix 流程

紧急修复（如数据错误修复、严重 Bug）可走简化流程，但不可绕过关键门禁。Hotfix 与快速通道的区别：

| 维度 | Hotfix | 快速通道 |
|------|--------|---------|
| **触发** | 紧急故障、数据错误 | 计划内小增补 |
| **发起方** | 任意时刻触发 | 需求分析Agent 分流决策后 |
| **Agent 边界** | 突破（单会话端到端，但 QA 验证独立） | 保持（五Agent 独立执行） |
| **版本计划** | 跳过 | 跳过 |
| **需求记录** | 事后补充完整 | 事前完成（需求分析Agent 产出） |
| **可追溯** | 事后补全追溯链（backlog 条目 + 测试用例 + 变更记录 + commit） | 事前完整追溯链（与标准通道一致，仅跳过 `plan/to-do/`） |

Hotfix 流程：

1. **快速诊断** — 明确问题根因和修复范围
2. **跳过版本计划** — 单个修复不需要 Goal→Epic→Story 拆分，无需写入 `plan/to-do/`
3. **保留需求记录** — 记录问题到 `requirements/requirements.md`，更新场景和测试用例（需求分析Agent 职责）
4. **保留实施与移交** — 实施修复后交付Agent 执行自测，移交至 `plan/verify/`（交付Agent 职责）
5. **保留独立验证** — QA Agent 执行定向验证 + 冒烟测试，通过门禁 4。若 QA 验证失败，按[回滚策略](#回滚策略)执行回滚（QA Agent 职责）
6. **保留发布记录** — 正常记录和提交（交付Agent 职责）
7. **事后回顾** — 在回顾中分析是否需要加强预防措施

> Hotfix 允许在单个会话中端到端完成（同时涉及规划侧和交付侧的文件修改），但必须在事后确保追溯链完整（需求记录、测试用例、变更记录、Git commit 全部到位）。

### 回滚策略

每个 Release Version 在版本计划的 Plan 文件中必须包含回滚方案：

- **代码回滚**：`git revert <commit_hash>` 即可
- **数据回滚**：数据文件在实施前备份到 `data/.backup/`，回滚时从备份覆盖还原
- **回滚后验证**：回滚完成后，重新运行冒烟测试确认系统恢复到变更前状态；验证数据完整性（记录数与变更前一致、关键字段值无残留）
- **回滚触发条件**：冒烟测试失败且 1 小时内无法修复（交付Agent 或 QA Agent 均可触发）
- **回滚后通知**：回滚完成后通知相关人员（用户/下游），在 `change-log/` 中记录回滚事件（版本号、失败原因、回滚步骤、受影响数据范围）

## 禁止事项

以下行为明确禁止，违反即视为流程违规：

1. ❌ 跳过阶段直接编码 — 无需求文档和方案直接改代码
2. ❌ 跳过测试直接提交 — 未通过定向验证就进入下一个 Story
3. ❌ 物理删除数据 — 任何情况下都使用逻辑删除
4. ❌ 违反项目依赖约束 — 如项目规定纯标准库，不得引入第三方依赖
5. ❌ 跨版本合并提交 — 一个 commit 只能属于一个 Release Version
6. ❌ 静默变更 — 修改已有行为不更新测试用例和文档
7. ❌ 需求分析Agent 直接修改代码 — 需求分析Agent 不碰源码目录的代码实现
8. ❌ 交付Agent 跳过 Plan 队列 — 必须从 `plan/to-do/` 拉取版本计划，不得绕过计划直接实施
9. ❌ 交付Agent 直接修改需求/定义 — 交付Agent 不修改 `define/`、`requirements/` 中的文档
10. ❌ QA Agent 修改源码 — QA Agent 不碰源码目录的代码实现，只执行测试和环境管理
11. ❌ 跨环境直接合并 — `dev → prod`、`qa → prod` 等跳过中间环境的直接合并均禁止，环境晋升必须经过 `qa → stg → prod`
